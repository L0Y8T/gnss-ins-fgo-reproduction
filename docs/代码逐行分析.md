## 1. `la.py` —— 为什么自己写线性代数库

### 1.1 `gauss_solve(A, b)`：高斯消元求解 $A\mathbf{x} = \mathbf{b}$

这是整份代码的心脏。每次 Gauss-Newton 迭代都要解一个 $4K \times 4K$ 的方程组。

算法三步（对应代码里注释的 3.1 / 3.2 / 3.3）：

```python
piv = k
for i in range(k + 1, n):
    if abs(M[i][k]) > abs(M[piv][k]):
        piv = i
...
if piv != k:
    M[k], M[piv] = M[piv], M[k]
```

为什么要选主元？假设主元是 $10^{-20}$，那么消元时 `factor = M[i][k] / 10^-20` 会得到一个天文数字，浮点误差被放大到不可接受。选绝对值最大的元素做主元，能把误差放大控制住。这一步叫「列主元（partial pivoting）」，是所有专业数值库的标准做法。

```python
pivval = M[k][k]
for i in range(k + 1, n):
    factor = M[i][k] / pivval
    for j in range(k, n + 1):
        M[i][j] -= factor * M[k][j]
```

这就是中学的「消元法」：第 $i$ 行减去 $\frac{M_{ik}}{M_{kk}}$ 倍的第 $k$ 行。做完之后，$k$ 列以下的元素全变成 0，矩阵变成上三角。

```python
x = [0.0] * n
for i in range(n - 1, -1, -1):
    s = M[i][n]
    for j in range(i + 1, n):
        s -= M[i][j] * x[j]
    x[i] = s / M[i][i]
```

上三角方程组里最后一行只有一个未知数，直接解出来；然后往上逐行回代。

### 1.2 一个踩过的坑：绝对阈值 vs 相对阈值

一开始的写法是：

```python
def gauss_solve(A, b, eps=1e-12):
    ...
    if abs(M[piv][k]) < eps:
        raise ValueError("矩阵奇异")
```

正确做法是用相对于矩阵最大元素的阈值：

```python
if eps is None:
    amax = max(abs(x) for row in A for x in row)
    eps = 1e-10 * amax
```

教训：数值线性代数里，永远用相对量而不是绝对量做判据。

#### 一个容易被推翻的理由

听起来很合理的理由是：正规方程 $H^TWH$ 里不同方向的信息量相差好几个数量级，所以主元可能很小，固定阈值会误判。

这个理由站不住，实测可以推翻它。

① 实测：真实的 $H^TWH$ 量级跨度很小

用本复现真实的 120 维正规方程（窗口 $K=30$），实测如下：

最大元素 6.859
非零最小元素 2.041
量级跨度 只有 3.4 倍
消元中最小主元 0.174

最小主元 0.174 比 $10^{-12}$ 大 1700 亿倍——绝对阈值在这个矩阵上根本不会误判。

② 为什么"信息量差几个数量级"不会造成小主元

因为正规方程是加权求和，不是加权相乘：

$$A = H^TWH = \sum_i w_i \cdot (h_i h_i^T)$$

每条约束是加进去的。小权重只是"贡献得少"，不会让矩阵元素变小。
矩阵的尺度由最大的那些权重决定。

③ 真正的理由：尺度不变性

把 $Ax=b$ 两边同乘一个非零常数，解不变。所以求解器对"换单位"必须免疫。
实测同一个方程缩放到 $10^{-12}$ 倍时：

下面每行的四个量依次是：缩放因子、矩阵最大元素、绝对阈值 $10^{-12}$ 的结果、相对阈值的结果。

$10^0$ 6.859 成功 成功
$10^{-6}$ 6.859e-06 成功 成功
$10^{-9}$ 6.859e-09 成功 成功
$10^{-12}$ 6.859e-12 报奇异 成功

同一个方程，只是换了个单位，绝对阈值就崩了。

#### 顺带认识一个更危险的失败模式

权重跨度大确实会害人，但不是以"小主元"的方式，而是静默失效：

如果某条约束的权重比别的小 8 个数量级以上，那条约束在数值上约等于不存在。
求解器不会报错——它给出一个"看起来正常"的答案，而那条约束根本没起作用。

 表现 危险程度

小主元 程序报错，立刻知道 低——会响的警报是好警报
静默失效 正常返回，结果悄悄是错的 高——不响的警报才要命

防法：不要只看会不会报错，要检查权重的跨度；超过约 $10^8$ 就要警惕。

### 1.3 `weighted_normal_equations(H, W, r)`：Gauss-Newton 的核心一步

这个函数实现的是论文式 (19) 的落地形式。

数学推导（代码注释里也有）：

代价函数 $J(\mathbf{x}) = \sum_j \|\mathbf{r}_j\|^2_{\Sigma_j}$，其中 $\mathbf{r}_j = h_j(\mathbf{x}) - \mathbf{z}_j$。

在当前点做一阶泰勒展开：$\mathbf{r}(\mathbf{x}_0 + \Delta\mathbf{x}) \approx \mathbf{r}(\mathbf{x}_0) + H\Delta\mathbf{x}$

代入并令导数为零：

$$\frac{\partial}{\partial \Delta\mathbf{x}}\left[(\mathbf{r} + H\Delta\mathbf{x})^TW(\mathbf{r} + H\Delta\mathbf{x})\right] = 2H^TW(\mathbf{r} + H\Delta\mathbf{x}) = 0$$

$$\boxed{(H^TWH)\,\Delta\mathbf{x} = -H^TW\mathbf{r}}$$

代码实现：

```python
sw = [w ** 0.5 for w in wdiag]
Hw = [[H[i][j] * sw[i] for j in range(n)] for i in range(m)]
rw = [[r[i][0] * sw[i]] for i in range(m)]

A = zeros(n, n); g = zeros(n, 1)
for i in range(m):
    Hi = Hw[i]; ri = rw[i][0]
    for a in range(n):
        ha = Hi[a]
        if ha == 0.0:
            continue
        g[a][0] += ha * ri
        for b in range(a, n):
            A[a][b] += ha * Hi[b]

for a in range(n):
    for b in range(a + 1, n):
        A[b][a] = A[a][b]
```

三个值得注意的点：

1. 白化（whitening）：与其构造一个大对角矩阵 $W$，不如把每个残差和雅可比行乘以 $\sqrt{w_i}$。这样 $H^TWH = H_w^TH_w$，省内存，也是 $\Sigma$ 非对角时的通用写法（用 Cholesky 因子）。它不改变条件数——两者是同一个矩阵，实测 cond 完全相同（比值 1.000000）。

2. `if ha == 0.0: continue`：因子图的雅可比矩阵极其稀疏（每一行只有 2–3 个非零元）。跳过零能让速度提升一个数量级——这对纯 Python 实现至关重要。

3. 只算上三角再补全：利用对称性，计算量减半。

## 2. `sim.py` —— 造数据

### 2.1 一个必须避免的坑：加速度不能写成纯随机游走

```python
a = [a[0] + _gauss(rng, cfg.accel_rw_std),
     a[1] + _gauss(rng, cfg.accel_rw_std)]

a = [cfg.accel_rho * a[0] + _gauss(rng, cfg.accel_rw_std),
     cfg.accel_rho * a[1] + _gauss(rng, cfg.accel_rw_std)]
```

用错误写法得到的结果：300 秒后速度涨到 437 m/s（约 1570 km/h），轨迹长达 74 km。这显然不是车辆。

为什么：纯随机游走的方差随时间线性增长（$Var(a_k) = k\sigma^2$），所以速度的方差按 $k^3$ 增长。加上回归系数 $\rho < 1$ 之后，加速度会有一个「回复力」把它拉回 0，方差收敛到稳态。

这是模拟随机过程时最经典的错误，一定要检查速度和加速度的物理合理性。

### 2.2 GNSS 异常值的造法：为什么要两个坐标轴用同一个标志

```python
is_out = ro.random() < cfg.gnss_outlier_ratio
bias = cfg.gnss_outlier_bias if is_out else 0.0
zx = s["p"][0] + _gauss(rg, sigma_k) + bias * 0.6
zy = s["p"][1] + _gauss(rg, sigma_k) + bias * 0.8
```

关键：`is_out` 是整个历元共用的，不是每个坐标轴独立判。

为什么：一栋楼挡住的是一颗卫星，它造成的偏差会同时出现在所有位置分量上。如果两个轴独立判异常，那就不像 NLOS 了，更像两个独立的测量故障。物理建模要讲究这个。

### 2.3 误差指标：为什么用「二维水平误差」

```python
def horizontal_error(est_p, true_p):
    dx = est_p[0] - true_p[0]
    dy = est_p[1] - true_p[1]
    return math.sqrt(dx * dx + dy * dy)
```

这是二维水平误差，与 Wen 2021 只评估 2D 精度的口径一致。如果是三维就要加上高程，而论文明确说它不评估高程（因为姿态来自 AHRS，高程精度不可靠）。

### 2.4 `metrics()` 里的 `burn_in`：为什么前几个历元要丢掉

```python
def metrics(errors, burn_in=0):
    e = errors[burn_in:]
    ...
```

前几个历元滤波器还没收敛（初始协方差是猜的、初始速度设成 0），误差会异常大。业界惯例是丢掉这段「暂态」。论文未说明是否做了 burn-in，这一点存疑。

## 3. `estimators.py` —— 核心中的核心

### 3.1 状态向量布局

```python
NX = 4
IDX_E, IDX_N, IDX_VE, IDX_VN = 0, 1, 2, 3
```

窗口内 $K$ 个历元的状态拼成 $4K$ 维向量。这个约定贯穿全文：历元 $g$ 的状态在总向量的第 $4g$ 到 $4g+3$ 位。

### 3.2 最重要的一个坑：运动模型因子不能约束速度

这是在调试中花了最长时间才定位的问题。

初版的写法（错误）：

```python
for d in (IDX_E, IDX_N):
    row[base_n + d] += 1.0
    row[base_g + d] += -1.0
    row[base_g + IDX_VE + (d - IDX_E)] += -dt
    ...

for d in (IDX_VE, IDX_VN):
    row[base_n + d] += 1.0
    row[base_g + d] += -1.0
    ...
```

错在哪：「$v_{g+1} = v_g$」隐含了「加速度 = 0」。而 IMU 因子说的是「$v_{g+1} = v_g + a\Delta t$」。两个因子直接冲突——模型一边用 IMU 说「车在加速」，一边又说「速度不许变」。

后果：窗口越长，这个自相矛盾的约束累积得越厉害，估计被系统性地「拉直」——趋势和论文完全相反。（那一版的具体数字没有保留在 results/ 里。）

正确写法（对照论文式 21）：

```python
for g in range(K - 1):
    for d in (IDX_E, IDX_N):
        row = [0.0] * n
        row[base_n + d] += 1.0
        row[base_g + d] += -1.0
        row[base_g + IDX_VE + (d - IDX_E)] += -dt
        ...

for g in range(K - 1):
    for d in (IDX_VE, IDX_VN):
        row = [0.0] * n
        row[base_n + d] += 1.0
        row[base_g + d] += -1.0
        ...
```

对照论文式 (21)：原文的 $h_{MM}$ 只写了 4 个块（3 个位置 + 零偏），没有速度行；速度的递推完全由 INS 因子（式 25）负责。

 顺带指出论文的一处问题：式 (21) 只写 4 个块，但式 (22) 给的协方差矩阵却是 6×6 的。这说明式 (21) 漏印了速度行。读者很容易在这里写错——这正是踩的坑。

### 3.3 权重必须从配置读，不能写死

一开始把论文里的值直接写死：

```python
q_pos2 = 0.3 ** 2
q_vel2 = 0.01 ** 2
s_v2 = (0.15 * dt) ** 2
```

后果：后来改了 `Config` 里的参数想做敏感性分析，结果结果完全不变——因为权重根本没读配置。白白浪费了一轮调试。

正确写法：

```python
s_p, s_v = sigma_motion(cfg)
s_imu_v = cfg.imu_velocity_sigma
q_pos2 = s_p ** 2
q_vel2 = s_v ** 2
s_v2 = s_imu_v ** 2
r_g2 = cfg.r_gnss
```

教训：数值实验里，任何可能要做敏感性分析的参数都必须从配置读。

### 3.4 滑动窗口的冷启动：为什么需要「初始速度先验」

问题：当窗口里只有 1 个历元时（$K=1$ 的第一个历元），运动模型因子和 IMU 因子都无处可挂，只剩一元 GNSS 位置因子 → 速度完全不可观 → 正规方程奇异。

代码里的处理：

```python
if v0_prior and K == 1:
    var_v0 = 25.0
    for d in (IDX_VE, IDX_VN):
        row = [0.0] * n
        row[d] += 1.0
        rows_H.append(row)
        rows_r.append([X_blocks[0][d] - 0.0])
        rows_w.append(1.0 / var_v0)
```

为什么方差给 25：这是一个「很弱」的先验（标准差 5 m/s），只是为了让矩阵不奇异，几乎不影响结果。物理上这叫「冷启动时假设静止」——实际系统里也是这么做的。

### 3.5 窗口含义的正确解读

```python
K = max(1, window)
...
g0 = max(0, k - K + 1)
idxs = list(range(g0, k + 1))
```

关键：`K` 是「新增历元数」，所以窗口里最多有 $K$ 个状态。

论文写 "window size of 1 s [K=1]"，但窗口只含 1 个状态时因子挂不上（见 3.4），所以物理上最小的有意义窗口是「2 个状态」。

### 3.6 `run_fgo()` 的主循环：warm start

```python
for k in range(n):
    g0 = max(0, k - K + 1)
    idxs = list(range(g0, k + 1))

    if g0 == k:
        if k == 0:
            X = [[cur[0], cur[1], cur[2], cur[3]]]
        else:
            prev = X_hist[k - 1]
            X = [[prev[IDX_E] + prev[IDX_VE] * dt, ...]]
    else:
        X = [list(X_hist[g]) for g in idxs[:-1]]
        prev = X[-1]
        new = [prev[IDX_E] + prev[IDX_VE] * dt, ...]
        X.append(new)

    gnss_idx = [g for g in range(g0, k + 1)]
    X, info = fgo_solve_window(cfg, X, gnss_idx, meas["gnss"], meas["imu"],
                               n_iter, verbose=verbose)

    for j, g in enumerate(idxs):
        X_hist[g] = list(X[j])
```

两个关键点：

1. `g0 == k` 判断而不是 `k == 0` 判断：初版用 `k == 0` 做判断，结果 $K=1$ 时第 2 个历元拿到一个空窗口，程序崩溃（`IndexError: list index out of range`）。边界条件的判断要针对真正的条件，不要用「启动阶段」这种间接特征。

2. warm start（热启动）：窗口里的历史状态直接用上一轮的估计做初值，新历元用运动模型外推。这让 Gauss-Newton 只需很少的迭代就能收敛（实测 1 次就够）。这是工程上必做的优化——如果每个窗口都从零开始，迭代次数会多得多。

3. `for j, g in enumerate(idxs): X_hist[g] = list(X[j])`：这一行就是「批处理会修正历史」的实现——窗口内所有历元的结果都被更新了，不只是最新那个。这正是 FGO 与 EKF 的本质差别。

### 3.7 `run_ekf()`：递归滤波

```python
x_pred = add(matmul(F, x), matmul(G, col(meas["imu"][k])))
FP = matmul(F, P)
FPFT = matmul(FP, transpose(F))
P_pred = add(add(FPFT, Qm), Gu_cov)

H = zeros(2, NX); H[0][0] = 1.0; H[1][1] = 1.0
y = sub(col(meas["gnss"][k]), matmul(H, x_pred))
S = add(matmul(matmul(H, P_pred), transpose(H)), R)
K = matmul(matmul(P_pred, transpose(H)), _inverse_2x2(S))
x = add(x_pred, matmul(K, y))
P = matmul(sub(identity(NX), matmul(K, H)), P_pred)
```

逐行对应卡尔曼滤波的五个标准方程：

代码 方程 含义

`x_pred = F x + G u` $\hat{x}^-_k = F\hat{x}^+_{k-1} + Gu$ 预测状态
`P_pred = F P Fᵀ + Qm + Gu_cov` $P^-_k = FP^+_{k-1}F^T + Q$ 预测协方差
`y = z - H x_pred` $\tilde{y}_k = z_k - H\hat{x}^-_k$ 新息（残差）
`S = H P⁻ Hᵀ + R` $S_k = HP^-_kH^T + R$ 新息协方差
`K = P⁻ Hᵀ S⁻¹` $K_k = P^-_kH^T S_k^{-1}$ 卡尔曼增益
`x = x_pred + K y` $\hat{x}^+_k = \hat{x}^-_k + K_k\tilde{y}_k$ 更新状态
`P = (I - KH) P⁻` $P^+_k = (I - K_kH)P^-_k$ 更新协方差

为什么用 `_inverse_2x2` 而不是通用高斯消元：这里只需要求一个 $2\times2$ 矩阵的逆，用解析公式比通用消元快得多，也更稳。

```python
def _inverse_2x2(S):
    a, b = S[0][0], S[0][1]
    c, d = S[1][0], S[1][1]
    det = a * d - b * c
    if abs(det) < 1e-15:
        raise ValueError("2x2 矩阵奇异")
    return [[d / det, -b / det], [-c / det, a / det]]
```

 一个公平性要点：注意 `Gu_cov` 用的是 `cfg.imu_velocity_sigma`，与 FGO 的 IMU 因子完全相同。这是公平对比的前提——如果 EKF 用一套噪声参数、FGO 用另一套，那测出来的差别就分不清是「算法差异」还是「调参差异」了。论文特意强调了这一点（"we used the same parameters for the EKF and FGO"）。

## 4. `experiment.py` —— 四组实验的设计

### 4.1 实验 1 的判据设计

关键代码：

```python
for K in [2, 5, 10, 30]:
    vals = []
    for it in [1, 2, 3, 5, 10, 20]:
        r = run_fgo(cfg, meas, window=K, n_iter=it)
        vals.append(summarize(r["errors"])["mean"])
    spread = max(vals) - min(vals)
    print(f"窗口 {K:>3}: 各迭代次数下均值范围 {min(vals):.4f} ~ {max(vals):.4f} m，极差 {spread:.3e} m")
```

为什么用「极差」做判据：如果迭代次数真的有用，那么 1 次和 20 次的结果应该差很多（米级）；如果没用，差异就只来自浮点舍入（$10^{-13}$ 级）。极差这个统计量直接把两种情形区分开了。

实测结果：极差 $3.6\times10^{-15}$ 到 $5.5\times10^{-13}$ m —— 确认无影响。

### 4.2 实验 3 的三段划分

```python
before = sum(e[D - 60:D]) / 60
after = sum(e[D:D + 60]) / 60
nearD = sum(e[D - 10:D + 11]) / 21
```

为什么要分三段：论文 4.4 节的反例是「在突变点附近大窗口更差」。如果只看整体均值，这个局部效应会被平均掉。必须针对性地看突变点附近。

## 5. 调试过程中踩过的坑（汇总）

这一节可能是全文档最有价值的部分。

# 坑 症状 根因 教训

1 PDF 文本提取粘连 `Factorgraphoptimization` 该 PDF 用 kerning 位移编码空格 数据源要先验证，不能假设工具可靠
2 加速度纯随机游走 速度涨到 437 m/s 缺回归项，方差无界增长 模拟随机过程后一定检查物理合理性
3 求解器绝对阈值 满秩矩阵误报奇异 判据没跟着问题尺度走 数值判据永远用相对量（理由见 §1.2）
4 运动模型多约束速度 长窗口反而更差（趋势反转） 与 IMU 因子冲突 仔细核对论文每个公式的维度
5 权重写死未读配置 改参数无效 硬编码 可调参数必须从配置读
6 窗口边界判断错误 `IndexError` 用 `k==0` 判断而非 `g0==k` 边界判断要对准真正的条件
7 不适用：`Q_imu` 是死代码（`Qi` 从未被读取，见 `code/estimators.py` 第 44 / 59 行）；实测把 `big` 从 1e2 扫到 1e12 结果不变 —— 判断代码行为只能靠实测，不能靠注释
8 窗口含义理解错 $K=1$ 时崩溃 混淆「状态数」与「新增历元数」 论文的措辞要结合物理意义解读
9 噪声参数照抄论文 窗口趋势完全相反 论文的速度项比实测残差紧约 27 倍 噪声协方差必须在自己的数据上标定
10 用错参数名做扫描 结果完全不变 `mm_scale` 在代码里不存在 做敏感性分析前先确认参数名存在

### 坑 9 的详细说明（最重要）

现象：照抄论文式 (22)(27) 的噪声参数后，窗口越大越差，趋势与论文相反。

排查过程：
1. 先怀疑求解器有 bug → 用「从真值出发解单个窗口」验证 → 求解器正确（解出的代价确实低于真值处代价）；
2. 再做「权重消融」→ 发现把 IMU 因子权重降到 1% 后，误差从 14.64 m 掉到 2.02 m → 定位到 IMU 因子权重过强；
3. 最后做「真值残差标定」→ 量出 IMU 因子实际残差 RMS 是 0.265 m/s，而论文假定 0.15 m/s（紧约 1.8 倍）。

结论：估计器假定的噪声如果远小于实际残差，它会拼命去满足一个不可能满足的约束，结果把估计拉偏。这正是论文 4.4 节所说的：

"if the error modeling is incorrect ... a larger window size will lead to only limited improvements or even worse accuracy"
